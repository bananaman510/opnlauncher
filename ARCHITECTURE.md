# Architecture

## Current application shape

- `src/` contains the React and TypeScript interface.
- `src-tauri/src/app.rs` exposes the small set of Tauri commands used by the interface and owns local process/log handling, including periodic play-session checkpoints while tracking is enabled.
- `src-tauri/src/microsoft_auth.rs` implements the experimental Microsoft public-client PKCE flow, Xbox/Minecraft entitlement checks, session refresh, and Linux Secret Service token storage. The frontend receives only verified account metadata; access tokens stay backend-only.
- `src-tauri/src/database.rs` owns the SQLite schema and instance/profile persistence, including per-instance provider/version references for installed mod files and opt-in local play sessions.
- `src-tauri/src/java.rs` discovers and inspects installed Java runtimes.
- `src-tauri/src/loaders.rs` retrieves official Fabric/Forge build metadata, installs Fabric profiles with verified libraries, runs checksum-verified Forge client installers for a selected game folder, and scans installed loader profiles.
- `src-tauri/src/minecraft.rs` inspects local game directories and version manifests, and discovers standard folders plus known third-party launcher instance folders without recursively scanning the full device.
- `src-tauri/src/launch.rs` resolves local version metadata and constructs a Java process plan.
- `src-tauri/src/downloads.rs` reads Mojang's official version manifest, resolves vanilla file metadata, verifies downloads, and installs into a new isolated instance directory. For Horizon, it can copy only checksum-matching files from a selected local installation into the private cache before downloading anything missing. Long network and file operations run on Tauri's blocking worker pool; progress is emitted as events.
- `src-tauri/horizon-upstream/` vendors the Rust source needed for Horizon's Minecraft 26.3 client and resource preparation, with upstream MIT and third-party notices preserved. `src-tauri/horizon-runtime/` builds the native game as a separate managed process, and `scripts/build-horizon-runtime.mjs` packages it for development and desktop bundles.
- `src-tauri/src/horizon.rs` validates the bundled Horizon Launch API, stages the small resource-preparation source inputs safely, constructs local-profile game commands, and manages per-instance `.hmod` content files. Its static Fabric adapter inspects JAR metadata and bounded `assets/`/`data/` entries, rejects Java execution features, validates generated Horizon packages, and prepares them immediately before launch. A separate opt-in code bridge setting is persisted per Horizon profile.
- `src-tauri/fabric-bridge/` contains a small Fabric `GameProvider`, a tightly scoped Fabric/Minecraft facade, and the event-forwarding helper. Before launch, Rust checks metadata and Java class references, then copies only allowlisted JARs to private staging. The helper JVM executes unchanged Java callbacks beside Horizon; bounded player, input, world-environment, and nearby-block snapshots plus a small set of explicit actions cross the bridge. This opt-in prototype is disabled by default and is not a Java-bytecode-to-Rust compiler or general Fabric compatibility layer. The Java + Fabric game backend remains a separate mode.
- `src-tauri/src/app.rs` also calls the vendored `horizon-prepare` library directly, stages prepared resources before replacing the shared cache, and resolves the included runtime from the development checkout or Tauri bundle.
- `src-tauri/src/mods.rs` queries the documented Modrinth and CurseForge APIs, filters projects and files by Minecraft version and loader, inspects existing mod JAR metadata, identifies older Modrinth installs by SHA-1 lookup on demand, verifies saved dependency versions and local integrity before reuse, and stages verified installs or replacements before changing files. The CurseForge API key is passed in memory from the UI and is not persisted.
- `src/pages/ModsPage.tsx` provides provider search, category/sort filters, project artwork and galleries, duplicate-install recognition, compatible build selection, dependency information, install progress, and local enable/disable, version-switch, multi-select, and confirmed bulk-removal controls.
- `src/components/PlaytimeCard.tsx` renders the Overview chart and controls local opt-in tracking; `src/playtime.ts` splits sessions into local calendar-day, week, or month buckets without a charting dependency.
- `src/pages/HorizonModsPage.tsx` separates native Horizon content management, the static-resource adapter, and the experimental code bridge. The code bridge is explicitly disabled by default and documents its limited API mappings, Java permissions, and unsupported game APIs.
- `src/pages/ModVersionSwitchDialog.tsx` lists project releases with search, Minecraft version, loader, and release-type filters plus date/version sorting; it blocks incompatible selections for the active instance.
- `src-tauri/capabilities/default.json` grants the window only Tauri's core defaults. The frontend has no unrestricted shell, filesystem, or process plugin.

Core Rust logic can be tested without enabling the Tauri desktop feature by using `cargo test --no-default-features --lib`. The desktop executable is built with the `desktop` feature.

## Local data and boundaries

Tauri's app data directory contains `opnlauncher.sqlite3`, logs, managed instance directories, per-launch native-library caches, and Horizon's shared Minecraft 26.3 files, preparer scratch data, and prepared resources. The database stores instance names, engine kind, game directory paths, version IDs, Java paths, memory settings, timestamps, optional play-session timestamps and durations, unverified local developer profile names and UUIDs, Microsoft account display metadata, and local settings. Playtime tracking is disabled by default and remains local; disabling it preserves existing history. Microsoft access and refresh tokens are not stored in SQLite; Linux refresh tokens use the desktop Secret Service. The default desktop build enables developer profiles in both development and release configurations. Horizon's source code is bundled; downloaded Mojang files and prepared resources are not.

Registered Minecraft installation directories are read by Rust and are left untouched by downloads from the general vanilla version browser. Per-instance setup can add a selected official Minecraft version into the chosen game folder, validating relative paths and HTTPS URLs, enforcing file and total size limits, verifying upstream checksums or declared sizes, and refusing to replace conflicting files. Mod downloads are placed in a per-install staging directory inside the selected `mods` folder, validated against trusted HTTPS hosts and provider hashes/sizes, and installed without replacing existing files. Mod version switches stage and verify the new build first, move the old root JAR into that staging directory, restore it if adding the replacement fails, and then update the local provider/version mapping. Bulk removal validates every selected JAR before removing any. Fabric libraries are resolved from either profile artifact records or safe Maven coordinates, restricted to launcher and Minecraft library hosts, checked against profile or Maven SHA-1 values, size bounded, and installed without replacing conflicting files. Forge installation uses the official Maven installer artifact after verifying its published SHA-1; it runs as a direct Java process (no shell) with the selected instance directory as its target, and existing launcher profile configuration is restored after that installer exits. The instance database stores the active version profile ID; Minecraft and loader versions are resolved from that profile's metadata, avoiding duplicate version settings. Launch arguments are derived from local version JSON. Native archive extraction rejects unsafe paths, symbolic links, duplicate files, and oversized archives, and each Java launch gets its own temporary native directory cleaned after process exit. Token values are redacted from captured game output.

## Planned separation

Account providers and mod-loader integrations remain separate from the UI. Microsoft sign-in uses a system-browser authorization-code flow with PKCE, checks the Xbox/Minecraft session and Java entitlement, and refreshes the session before Java launch. The current credential adapter is Linux-only; Windows/macOS authentication remains disabled until secure platform credential stores are implemented. The vanilla installer does not yet support pause/resume, repair, or a persistent download queue. Loader installation currently supports Fabric and Forge; NeoForge and Quilt profiles can be detected and selected when already installed, but their installers are not implemented. Horizon `.hnmod` compilation and the isolated native executable lifecycle are not yet implemented because this checkout does not include Horizon's separate pinned compiler/build tooling. Existing Horizon `.hmod` content mods remain supported. Mod-provider requests target documented public APIs, with artwork loaded only from provider CDN hosts.
