# Horizon integration

OpnLauncher includes Horizon's Rust Minecraft 26.3 client and the Rust resource preparer. Horizon is a separate game engine: it has its own instance folders, worlds, settings, local player data, and `.hmod` content mods. The optional Fabric code bridge runs Java callbacks beside the Rust engine and maps client ticks, player position and floored block-position/velocity/look-direction/health snapshots, world-clock/build-height/weather snapshots, loaded block IDs and basic flags in a bounded 3×3×3 area around the player, read-only vanilla movement bindings and press edges, sprint control, bounded local-player velocity and look-direction requests, plain system chat, and HUD action-bar text. It does not translate arbitrary Java bytecode into Rust or provide general Fabric compatibility. The separate Java + Fabric backend runs the Minecraft Java client. OpnLauncher does not yet install or compile Horizon `.hnmod` native code mods.

## Included source and licenses

The vendored source is from Horizon commit `fdd290b99b4459cb4803487758ba8015a45aa47f`. The game runtime is built as a separate process and bundled by Tauri; resource preparation calls the included `horizon-prepare` Rust library. You do not need a separate Horizon checkout, client executable, or preparer executable.

Horizon source is MIT licensed. The upstream license and third-party notices remain in `src-tauri/horizon-upstream/LICENSE` and `src-tauri/horizon-upstream/THIRD_PARTY_NOTICES.md`. OpnLauncher remains GPL-3.0-or-later. The vendored source contains no Minecraft jars, assets, prepared resources, user data, or Horizon Git metadata. The launcher downloads the official game files only when you request preparation.

## Requirements

- A local OpnLauncher developer profile. These profiles are unverified and do not sign in to Microsoft.
- JDK 25, including `javac`, when preparing Horizon resources.
- Internet access when official Minecraft files need downloading or repair.
- For Linux development and AppImage builds, the system libraries required by Tauri. ALSA development files are required for Horizon audio; the build stops with an install hint if they are missing. `libudev` development files add optional controller support, but are not required for audio.

## Prepare and launch

1. In **Settings → Java manager**, add or choose a JDK 25 runtime. Horizon's exporter tools need both `java` and `javac`.
2. Create a Horizon instance from **Versions** or **Add an instance**.
3. Open **Horizon** and choose an existing Minecraft 26.3 folder, add a folder, or leave the source unset to download files into OpnLauncher's private cache.
4. Select **Download files & prepare Horizon**. OpnLauncher reuses only files verified against Mojang metadata, fetches missing official files over HTTPS, and calls the bundled Rust preparer. It then copies the pinned sound assets into Horizon's resources and checks that preparation is complete. Sound import copies about 380 MB from the verified local Minecraft asset store. OpnLauncher does not modify the selected Minecraft source folder.
5. Choose the Horizon instance and a local developer profile, then press **Play**.

The client, preparer source inputs, downloaded Minecraft files, prepared resources, and logs are managed separately from normal Java instances. Worlds and local settings remain in each Horizon instance. Preparing or launching Horizon does not change standard Minecraft profiles.

## Optional Fabric resource bridge

The Horizon mod workspace has a separate **Fabric bridge** tab. It reuses the Modrinth and CurseForge browser to find provider builds tagged for Minecraft 26.3 and Fabric, and installs them into the selected Horizon profile's `mods/` folder. Bridge settings are per profile and the feature starts disabled.

When enabled, OpnLauncher inspects those JARs once immediately before each Horizon launch. Only standalone JARs with safe, code-free `assets/` and `data/` entries may be copied into generated Horizon `.hmod` content packages. The packages are checked using Horizon's manifest and content validators, written to the profile's `horizon-mods/` folder, and enabled for that launch. The process runs before Horizon starts; no adapter work continues during gameplay. Source JARs are preserved, and existing Horizon content namespaces are checked for conflicts.

This does not load Fabric Loader, run Java bytecode, implement Fabric APIs, or translate ordinary Fabric mods into Rust. JARs containing classes, entrypoints, mixins, access wideners, nested JARs, additional Fabric dependencies, unsupported paths, or resource formats Horizon rejects are skipped. Most gameplay and library mods, including Fabric API, are therefore not supported. The screen reports visible candidates/skips, and launch logs list any files rejected during package validation. Treat third-party archives as untrusted input.

Turning the bridge off disables the generated Horizon packages it manages but keeps the source JARs and generated files on disk. Removing a source JAR disables its generated package at the next launch. The native `.hmod` content workflow remains separate, and Java instances keep their normal Fabric/Forge behavior.

## Optional Java + Fabric runtime

Each Horizon profile can install a separate Minecraft 26.3 + Fabric Loader runtime under `.opnlauncher/fabric-java/` in that profile's folder. It has its own `versions/`, `libraries/`, `assets/`, `mods/`, and `saves/`; it does not share or overwrite the native Horizon world/mod paths or a normal Minecraft instance. Installation checks Java 25 or newer and validates that the selected loader profile targets Minecraft 26.3. Existing `.jar` and `.jar.disabled` files in the profile's top-level `mods/` folder are copied into the private runtime when their names do not already exist there; the original files are never removed or overwritten.

After installing, enable **Use Java + Fabric for this profile** in **Horizon → Selected profile settings → Fabric mods on this profile**. The launcher then starts the Java game client with a local, unverified profile, and the ordinary Mods page uses that private runtime's Fabric metadata and mod folder. Compatible Fabric JARs, including Fabric API and Sodium, remain unchanged and execute in Minecraft Java. This Horizon profile path currently accepts local profiles only; Microsoft account authentication is available only for regular Java instances. Disable the option to return to the native Rust Horizon launch; the isolated Java files and mods remain available for switching back.

This is a backend choice, not Fabric Loader ported to Horizon. It does not translate Java to Rust, call Rust game APIs from arbitrary Fabric code, or make mods run in Horizon's native renderer/world. Compatibility follows the mod's support for Java, Fabric Loader, and Minecraft 26.3. The optional runtime is experimental and still needs in-game validation from a development build.

## Experimental Fabric code bridge for native Horizon

The **Fabric** tab under **Horizon → Mods** has an independent, opt-in **Fabric code bridge** switch. It is off by default. When enabled and the profile is launched in native Rust mode, OpnLauncher starts Fabric Loader in a helper JVM using the selected Java 25+ runtime and loader installation. Rust inspects each installed Fabric JAR and accepts only `main`/`client` initializers whose classes use the mapped lifecycle, player/environment snapshots, bounded nearby block reads, velocity, rotation, keyboard key-mapping, sprint, bounded velocity setter, system-message, and action-bar APIs and no unsupported Minecraft APIs. It also checks entrypoint class paths, rejects duplicate enabled mod ids, and caps the inspection/staging work. Accepted JARs are copied unchanged into `.opnlauncher/fabric-code-bridge/mods/`; unsupported files and the installed Fabric API JAR are not passed to that helper. OpnLauncher supplies a narrow 26.3 Fabric API and Minecraft facade. Horizon queues `START_CLIENT_TICK` and `END_CLIENT_TICK` in order, each with player position, velocity, yaw/pitch, health/state, world time/build-height/weather, nearby loaded blocks, and bounded movement-input snapshots captured at its native tick boundary. The helper processes callbacks asynchronously, so delivery may lag or drop if the bounded queue fills. `Minecraft.level.getDayTime()` and `getGameTime()` read captured clocks; `Level` also exposes build-height bounds and rain/thunder state and levels from the same snapshot. `Level.getBlockState(BlockPos)` reads only the block cells captured within one block of the local player's feet. The returned state maps the block ID, `isAir()`, `isSolid()`, and `isSolidRender()`; unloaded cells and positions outside the capture are unavailable, and block properties, fluids, and mutations are not mapped. `Entity.getDeltaMovement()` returns an immutable `Vec3` snapshot with mapped coordinates and length calculations; `Entity.getYRot()` and `getXRot()` read captured local-player yaw and pitch. `Minecraft.options.keyUp`, `keyDown`, `keyLeft`, `keyRight`, `keyJump`, `keyShift`, and `keySprint` expose read-only vanilla movement mappings; `KeyMapping.isDown()` reads held state and `consumeClick()` consumes a press edge. These fields report Horizon's mapped vanilla movement actions only during active play. `KeyMappingHelper.registerKeyMapping(...)` registers a binding using its declared default key. `Entity.setSprinting(boolean)` queues a sprint request and `Entity.setDeltaMovement(Vec3)` queues a velocity request back to Horizon's Rust game thread. Both apply only during active play; velocity magnitude is limited to 4 blocks per tick. `Entity.sendSystemMessage(Component)` returns plain text to Horizon's native system chat, where the chat-visibility setting applies. `Minecraft.gui.hud.setOverlayMessage(Component.literal(text), animate)` returns plain text to Horizon's Rust action bar. Other Java calls do not directly mutate Horizon. If the Java helper starts or stops unexpectedly, the native Horizon game remains independent and the bridge stops forwarding events.

This is a deliberately narrow API mapping. Alongside tick, world-time, build-height, and weather snapshots, the bridge maps loaded block IDs and basic flags inside the bounded 3×3×3 capture around the player. Other mapped APIs include local-player position/velocity, health/state, `Entity.getDeltaMovement()` and selected immutable `Vec3` coordinate/length operations, `Entity.getYRot()` and `getXRot()` rotation reads, `Entity.setYRot(float)` and `setXRot(float)` look writes, plain `Entity.sendSystemMessage(Component)` calls, simple action-bar calls, and Fabric `KeyMappingHelper.registerKeyMapping(...)`, `getBoundKeyOf(...)`, `KeyMapping.isDown()`, and `KeyMapping.consumeClick()` for keyboard keys using Minecraft 26.3's SDL/HID key values. `Minecraft.options` exposes the seven read-only vanilla movement mappings; these report held state and press edges from Horizon's mapped actions. Mod bindings use their declared default key. It maps `Entity.setSprinting(boolean)` and `Entity.setDeltaMovement(Vec3)` as player-state writes; velocity requests must be finite and have magnitude at most 4 blocks per tick. Look requests require finite yaw within ±360,000 degrees and pitch from −90 to 90 degrees. Horizon applies those three action types on its game thread only during active play. Rotation writes update the local player's view/body only; they do not affect other entities or send an authoritative server change. System chat carries plain text and follows Horizon's chat-visibility setting; styles and click events are not translated. Velocity-vector methods beyond the explicit allowlist remain unsupported. The Options facade cannot edit bindings or provide conflict contexts; mouse/controller bindings and Java Options-screen integration are not provided. The helper does not load Minecraft's Java client JAR. The scanner rejects Mixin configs, access wideners, nested JARs, other Fabric API references, and unmapped Minecraft class/member references before code is loaded. Unsupported files are shown as rejected and excluded from the helper folder. General block/chunk APIs beyond the captured nearby cells, other entities, dimensions, registries, rendering, other player changes, and other lifecycle events are not mapped. Sodium's renderer is unsupported. In `.42`, the bridge adds environment and bounded nearby block snapshots with scanner, facade, and loopback coverage; these remain synthetic API tests and have not been tested in a live Horizon session or with a third-party mod.

To try it, install the profile's Minecraft 26.3 Fabric Loader in **Horizon settings**, install a mod from the Horizon **Mods** page, review its compatibility status, and turn on **Fabric code bridge**. Keep **Use Java + Fabric for this profile** turned off to launch the Rust engine. Only JARs marked **Mapped API subset** are staged; that status means the file passes the current static allowlist, not that it provides an in-game effect. A compatible test mod can read the local-player snapshot, send a plain system message, call the action-bar method, register and poll a default keyboard key, request a sprint toggle, set bounded velocity, or change the local look direction. Existing profile JARs are not rewritten. Turn the switch off to stop loading Java code on the next launch.

The mapped `Entity.blockPosition()` returns an immutable `BlockPos` view of the local player's latest position snapshot. Its `getX()`, `getY()`, and `getZ()` methods use Minecraft-style floor behavior (for example, `-3.5` becomes block `-4`). `Level.getBlockState()` can read loaded cells in the captured 3×3×3 region around that position; it does not provide general chunk access or arbitrary world queries.

The read-only `Level` facade maps `getDayTime()`, `getGameTime()`, `getMinBuildHeight()`, `getMaxBuildHeight()`, `isRaining()`, `isThundering()`, `getRainLevel(float)`, and `getThunderLevel(float)` from Horizon's per-tick environment snapshot. Its block-state view exposes only captured nearby cells and basic identity/flags, not chunks, properties, fluids, or Java world objects.

For a known-good test mod, build the development probe with `npm run fabric:build:probe` after building OpnLauncher. Copy `src-tauri/target/horizon-fabric-bridge-probe.jar` into the selected Horizon profile's `mods/` folder. With native Rust mode and the code bridge enabled, it should display the player's name, coordinates, block coordinates and captured block ID/basic flags, velocity and horizontal speed, yaw, pitch, health, sprint state, ground state, world time, game time, build-height limits, and rain/thunder values once the local player is available. Press and hold **P** to see the held-key message; while moving forward, tap **P** to check `Minecraft.options.keyUp` and `keyShift`, consume a forward press edge, request sprint, queue a small vertical velocity change, turn the view by 90 degrees and 15 degrees pitch, send a system chat message, and display a separate action-bar response. Without a player it displays a connection message. The test JAR is a development fixture and is not included in the application bundle.

Java mods run with the user's operating-system permissions and are not sandboxed. They may access files and use the network as the user. The feature makes no additional network request itself; install only code from sources you trust.

## Offline and privacy behavior

Horizon launches use local, unverified profiles. OpnLauncher does not pass Microsoft authentication tokens to Horizon, and local Horizon profiles do not verify ownership. Regular Java instances can use the experimental Microsoft account flow described in the main README. The Horizon child process receives `HORIZON_TELEMETRY_URL=off`, disabling Horizon telemetry and its play ping. Resource preparation contacts Mojang's official metadata and file hosts only when that feature is requested. No OpnLauncher-operated server is used.

Local profiles are for offline single-player development and appropriately configured local testing. They do not authenticate to online servers or bypass Minecraft ownership checks. Downloaded Minecraft files remain local and are not bundled or redistributed.

## Current limits

Horizon support, the static resource adapter, the small Fabric code bridge, and the Java + Fabric backend are experimental; Horizon is fixed to Minecraft 26.3, matching the vendored upstream source. The maintainer has reported successful local native play. The code bridge has passed synthetic loopback and official Fabric Loader checks, including the sprint-action path, but it has not been validated in a live Horizon session or against a third-party Fabric mod. It does not provide general Fabric API compatibility.

### Horizon native code mods (`.hnmod`)

Horizon `.hnmod` files are Rust source bundles that Horizon's native build pipeline applies to pinned game source and compiles into a separate executable. They are not loadable plugins or `.hmod` content packs. Native code runs with the user's operating-system permissions, so every install/build needs a clear, explicit trust decision. The vendored Horizon source includes the bundle validator, but this OpnLauncher build does not include Horizon's isolated native compiler, pinned Rust toolchain/build cache, per-instance executable management, or native-mod registry workflow. Installing and running `.hnmod` files is therefore not supported yet. Existing Horizon `.hmod` content mods remain supported as documented above.
